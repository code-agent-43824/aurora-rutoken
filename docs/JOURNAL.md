## 2026-07-30 — Claude: КриптоПро на NFC-пути, экономия CAPI-чтений (1.2.0-8)

**Device-smoke `1.2.0-7` (владелец):** ключи склеиваются, лишние контейнеры
исчезли, путь контейнера печатается в карточке сертификата. Новые задачи.

**КриптоПро на NFC.** Функции CSP работали только по USB. По NFC читать CAPI
можно лишь пока устройство поднесено, поэтому проход встраивается в то же
поднесение: мастер `NfcConnectPage` после чтения PKCS#11, если CSP включён,
дочитывает контейнеры и только потом просит убрать устройство. Результат
сохраняется снимком в `TokenSession` рядом с `nfcObjects`, поэтому объекты
КриптоПро остаются видны после отрыва и переживают подключение других устройств.

**Экономия чтений.** Владелец отдельно указал: чтение через КриптоПро заметно
медленнее PKCS#11 даже по USB. Раньше любое изменение набора устройств вызывало
полный CAPI-проход, включая отрыв NFC и извлечение USB, когда читать уже нечего.
Теперь решение принимает `CryptoProSession::syncWithTokens`: проход запускается
только если изменился набор считывателей и хотя бы одно устройство на связи;
пропажа устройств лишь запоминается, а последний снимок сохраняется. Операции
записи по NFC CAPI-проход не запускают.

**Двойной источник.** Объект, видимый обоими интерфейсами, показывает «PKCS#11 и
КриптоПро CSP»: это и точный DER-дубликат сертификата, и случай, когда открытый
ключ сертификата PKCS#11 совпал с ключом контейнера КриптоПро.

**CI-прогон (run #78, `0fe5978`) — ЗЕЛЁНЫЙ с первой попытки.** Обе архитектуры
собраны без предупреждений, официальный валидатор принял оба пакета, в
`ci-latest` четыре RPM `1.2.0-8` (`…armv7hl.rpm` 228 669 Б, `…aarch64.rpm`
238 003 Б + официальная библиотека). Host-проверки: гейт инвариантов (добавлены
регрессии на NFC-снимок CSP, запрет безусловного прохода в `main.cpp`, двойной
источник и фильтрацию строки версии), скобки QML, переводы 0 пропусков /
0 незавершённых, XML валиден, версия синхронизирована.

**Версия КриптоПро.** Строка дублировалась: обработчик фоновых строк
диагностики отфильтровывал только `cryptoprolib`, но не `cryptoprover`, поэтому
версия добавлялась дважды. Отфильтрованы оба идентификатора. Версия дополнена
номером сборки: `PP_VERSION` даёт только `5.0`, поэтому helper ищет более полную
версию в метаданных установленного пакета и в именах файлов каталога CSP и
использует её, если она согласуется с major.minor от провайдера.

## 2026-07-30 — Claude: склейка контейнера с сертификатом по открытому ключу (1.2.0-7)

**Device-smoke `1.2.0-6` (владелец):** сертификат из контейнера читается, виден
до и после ввода PIN-кода, в заголовке Common Name — три замечания предыдущей
итерации закрыты. Найдено новое: на экране висят два самостоятельных контейнера
`…\pkcs_key_02f4` и `…\pkcs_key_020f`. Владелец: эти ключи почти наверняка
принадлежат показанному сертификату, и отдельно их видеть не нужно — ключ должен
быть дочерним объектом своего сертификата.

**Причина.** У этих контейнеров нет собственного сертификата: `KP_CERTIFICATE`
пуст, поэтому проход 1.2.0-6 их не «представил», и модель честно показала их
самостоятельными объектами. Связь контейнера с сертификатом по имени
недоказуема (имена разные: у сертификата контейнер `78b3…`, у ключей —
`pkcs_key_*`), а угадывать нельзя — именно из-за угадывания в 1.2.0-4 терялся
реальный контейнер.

**Решение — связь по открытому ключу**, ровно тем же приёмом, которым сертификат
приклеивается к ключевой паре при импорте (v0.4). Для каждого контейнера
экспортируется открытый ключ (`CryptExportKey(PUBLICKEYBLOB)` — публичные
данные, read-only), для каждого сертификата извлекается открытый ключ из
`SubjectPublicKeyInfo`. Сопоставление идёт с сертификатами **обоих** источников:
объекты PKCS#11 получили поле `publicKeyHex` (общий помощник
`pkcs11::publicKeyFromCertificate`, переиспользующий уже проверенный парсер
импорта), сертификаты КриптоПро — своё, через локальный разбор DER в адаптере.
Сравнение — вхождением с проверкой обратного порядка байт ГОСТ (RFC 4491), так
как раскладка BLOB'а провайдера не специфицирована. Совпал — контейнер считается
представленным и отдельной строкой не показывается; не совпал, экспорт не
поддерживается или символа нет — поведение прежнее, контейнер остаётся видимым.

**Остальные замечания.** Путь контейнера добавлен и на экран самого сертификата
(`CertificatePage`, поле «Контейнер» рядом с `CKA_ID`), в списке он уже был.
Диагностика теперь показывает версию всего КриптоПро CSP: версия провайдера
через `CryptGetProvParam(PP_VERSION)` плюс, если найдётся, версия установленного
пакета из манифеста Авроры; строка про `libcapi20.so` сохранена. Список
библиотек остаётся честным — владелец подтвердил, что фактически загружается
только CapiLite, остальной CSP живёт отдельным сервис-процессом.

**Решения владельца зафиксированы:** (1) если CAPI потребует PIN-код, запрашиваем
его сами и передаём, а не отдаём провайдеру — для чтения сертификата PIN-код не
понадобился, поэтому реализация отложена до появления реальной необходимости;
(2) имена контейнеров считаем такими же, как в Linux, — своих форматов не
изобретаем.

**Проверки на хосте:** гейт инвариантов зелёный (добавлены регрессии на
`PUBLICKEYBLOB`, склейку в `TokenPage`, отпечаток у объектов PKCS#11, поле
«Контейнер» и `PP_VERSION`), `bash -n` пройден, скобки всех QML сбалансированы,
переводы 0 пропусков / 0 незавершённых (добавлены «Container» и «CryptoPro CSP
version»), XML валиден, версия `1.2.0-7` синхронизирована. Полная сборка — в CI.

**Первый прогон (run #76) КРАСНЫЙ — компиляция.** `cryptoProPackageVersion()`
вызывала `QJsonDocument::object()`, а `QJsonObject` в этом файле не подключён:
`error: invalid use of incomplete type 'class QJsonObject'` на обеих
архитектурах. Qt на хосте агента нет, поэтому такую ошибку ловит только сборка.
Исправлено без нового заголовка — тем же идиомом, что уже используется в этом
файле при разборе ответа helper'а: `document.toVariant().toMap()`.

**CI-прогон (run #77, `8c6e362`) — ЗЕЛЁНЫЙ.** Обе архитектуры собраны в Aurora
PSDK без единого предупреждения, официальный RPM-валидатор принял оба пакета
(`rpm_arch`/`elf_machine`/loader, подпись OMP regular, helper-режимы и

## 2026-07-30 — Claude: план чтения сертификата из контейнера КриптоПро (1.2.0-6)

**Device-smoke `1.2.0-5` (владелец):** контейнеры появились — на Рутокен Lite
контейнер виден, пункт 1 отчёта подтверждён. Открыты три замечания.

**Главное замечание — смысловая ошибка модели сертификатов.** Владелец указал:
нельзя путать сертификаты, которые видны через CapiLite-перечисление, с
сертификатами, которые физически лежат **внутри контейнера**. Перечисление
хранилища возвращает только **установленные (зарегистрированные)** сертификаты;
приложение их не регистрирует и регистрировать не будет, поэтому в этом списке
они не появятся никогда. Аудит кода подтверждает диагноз буквально: в
`scan()` единственный источник сертификатов — `CertOpenSystemStoreA(0, "MY")` +
`CertEnumCertificatesInStore`, а в минимальном ABI (`cryptopro_capi_minimal.h`)
нет ни одной функции работы с ключом контейнера. То есть внутрь контейнера
приложение не заглядывает вообще, и на носителе без установленных сертификатов
список закономерно пуст.

**План до кода.** Добавить второй, основной источник: открывать контекст самого
контейнера `CryptAcquireContextA(container, provider, type, CRYPT_SILENT)` и
читать привязанный к ключу сертификат `CryptGetUserKey(AT_KEYEXCHANGE /
AT_SIGNATURE)` → `CryptGetKeyParam(KP_CERTIFICATE)` → DER, затем
`CryptDestroyKey`/`CryptReleaseContext`. Минимальный runtime-ABI расширяется
тремя функциями и тремя константами; отсутствие символов деградирует к прежнему
поведению, а не ломает сканирование. Флаг `CRYPT_SILENT` обязателен: он
запрещает CSP поднимать системный запрос PIN, поэтому защищённый контейнер
вернёт ошибку вместо блокировки ограниченного helper-процесса и останется
обычным read-only объектом-контейнером. Сертификат из контейнера дедуплицируется
по точному DER с зарегистрированным и с PKCS#11 — приоритет PKCS#11 сохраняется,
а контейнер с показанным сертификатом помечается представленным.

**Замечание по интерфейсу.** В заголовке карточки должен быть **Common Name**, а
имя и путь контейнера — в строке метаданных, там же, где для PKCS#11-сертификатов
выводятся `CKA_LABEL`/`CKA_ID`. Сейчас контейнерная карточка ставит путь
заголовком (`label: container.name`), а путь контейнера у сертификата не
показывается вовсе — исправляется вместе с основным дефектом.

**Замечание по диагностике.** Владелец видит единственную `libcapi20.so`.
Разбор `/proc/self/maps` расширяется на модули КриптоПро вне известных каталогов
по имени файла. Если фактически в helper отображается только CapiLite (остальной
CSP работает отдельным сервис-процессом), диагностика скажет это честно —
выдумывать строки запрещено.

**Порядок работ:** сначала полностью доделать v1.2 до нормальной работы
(указание владельца), только затем v1.3 и бэклог. Кандидат — `1.2.0-6`;
обязательны source/RPM-регрессии, обе PSDK-архитектуры, официальный валидатор и
проверка публикации. Заодно сняты устаревшие пункты плана — физические проверки
`1.2.0-2` и `1.2.0-3`, перекрытые проверкой `1.2.0-5`.

**Реализация (1.2.0-6).** Минимальный runtime-ABI расширен тремя
необязательными функциями (`CryptGetUserKey`, `CryptGetKeyParam`,
`CryptDestroyKey`) и константами `AT_KEYEXCHANGE`/`AT_SIGNATURE`/
`KP_CERTIFICATE`; символы разрешаются после выбора библиотеки, их отсутствие
оставляет прежнее поведение. Новая `readContainerCertificates()` открывает
контейнер по FQCN (с запасными именами) без `CRYPT_VERIFYCONTEXT`, но строго с
`CRYPT_SILENT`, читает ключ обеих спецификаций и берёт привязанный сертификат
`KP_CERTIFICATE` с ограничением размера, затем освобождает ключ и контекст. В
`scan()` добавлен проход по логическим контейнерам после чтения хранилища:
известный по DER сертификат не дублируется, найденный привязывается тем же
`containerKey`, поэтому контейнер автоматически считается представленным и не
даёт вторую строку. Построение строки сертификата вынесено в общий
`buildCertificateRow()` — оба источника («store» и «container») дают одинаковый
набор полей, добавлено поле `origin`.

Интерфейс: карточка сертификата КриптоПро получила поле `container`, которое
выводится в строке метаданных как «контейнер: …» — рядом с местом, где для
PKCS#11 показываются `CKA_LABEL`/`CKA_ID`; заголовок остаётся Common Name.
Контейнерная карточка больше не ставит путь заголовком: заголовок — родовое
«Ключевой контейнер», путь ушёл в `idText` (место `CKA_ID`).

**Точность read-only-инварианта.** Гейт `ci/check-source-invariants.sh`
блокировал шаблон `CryptDestroy`, из-за чего запрещал `CryptDestroyKey` —
освобождение дескриптора ключа в памяти, парное к `CryptGetUserKey`. Оно ничего
не удаляет на носителе, а его отсутствие означало бы утечку. Запрет заменён на
перечень фактически изменяющих операций (`CryptGen*`, `CryptImportKey`,
`CryptSetProvParam`, `CryptSetKeyParam`, `CertAdd*`, `CertDelete*`,
`CRYPT_DELETEKEYSET`/`DeleteKeyset`), поэтому удаление контейнера и запись в
хранилище по-прежнему невозможны. Добавлены положительные регрессии: наличие
`KP_CERTIFICATE`-пути, тихого открытия контейнера, дедупликации по SHA-256,
строки «контейнер: %1» и запрет пути в заголовке карточки.

**CI-прогон (run #75, `5e963e2`) — ЗЕЛЁНЫЙ с первой попытки.** Обе
архитектуры собраны в Aurora PSDK; новый путь чтения контейнера
(`cryptoprosession.cpp`) скомпилирован под `-Wall -W` без единого
предупреждения. Официальный RPM-валидатор Авроры принял оба пакета; проверка
подтвердила `rpm_arch`/`elf_machine`/loader, подпись OMP regular, наличие
CMS/CAPI-QML, helper-режимов и permission CSP. В `ci-latest` атомарно
опубликованы ровно четыре RPM (`…-1.2.0-6.armv7hl.rpm` 220 610 Б,
`…-1.2.0-6.aarch64.rpm` 229 809 Б + официальная библиотека под обе арки).

**Проверки на хосте:** `ci/check-source-invariants.sh` зелёный, `bash -n`
пройден, ABI-заголовок компилируется отдельно (LP64; ILP32-смещения проверит
armv7hl в CI, форма `N * sizeof(void*)` арх-независима), скобки всех QML

`main.cpp` и spec. Полная сборка — в CI (Qt на хосте нет).

## 2026-07-30 — Watson: план CryptoPro-only объектов и полной runtime-диагностики

**Device-smoke владельца:** event-driven наблюдение в `1.2.0-4` подтвердилось —
Рутокен больше не мигает в покое. Однако Рутокен Lite без объектов закрытых и
открытых ключей PKCS#11 показывает пустой экран, хотя на нём есть контейнеры
КриптоПро. На Рутокен ЭЦП также не виден отдельный контейнер CSP, намеренно не
доступный через PKCS#11, как до входа, так и после него.

**Причина в текущей модели:** helper перечисляет самостоятельные CAPI-контейнеры,
но общий экран объединяет только `cryptoProSession.certificates`. Поэтому любой
контейнер без связанного сертификата теряется независимо от результата PKCS#11;
ошибка поиска объектов лишь делает этот дефект особенно заметным на Рутокен
Lite. Для сертификатов точный DER уже даёт безопасный приоритет PKCS#11, но
физический ключ связи сертификата с логическим CAPI-контейнером удаляется перед
передачей JSON.

**План до кода:** вернуть стабильный неприватный `containerKey` и в строках
контейнеров, и в связанных сертификатах. Объединять PKCS#11-список как
необязательный приоритетный источник: его пустота или ошибка не отменяет
CAPI-модель. Точный PKCS#11 DER скрывает CAPI-сертификат и одновременно отмечает
его контейнер представленным; видимый уникальный CAPI-сертификат также
представляет контейнер. Оставшиеся контейнеры соответствующего считывателя
показывать самостоятельными read-only объектами КриптоПро без операций PKCS#11.

Диагностика должна отражать не предполагаемый единственный файл, а фактический
runtime-набор. После CAPI-вызовов изолированный helper прочитает собственную
карту загруженных ELF из `/proc/self/maps`, отфильтрует пути пакета КриптоПро,
добавит непосредственно загруженную `libcapi20.so`, нормализует и вернёт
уникальный список. Основной процесс передаст его диагностике, которая создаст
отдельную строку на библиотеку только при включённом CSP. Это согласуется с
официальным руководством КриптоПро для Авроры: `libcapi20.so` является
CryptoAPI-интерфейсом, а CSP включает дополнительные библиотеки поддержки.
Кандидат — `1.2.0-5`; обязательны source/RPM-регрессии, обе PSDK-архитектуры,
официальный валидатор и проверка публикации.

**Реализация:** `c843c38`. CAPI-helper теперь сохраняет публичный стабильный
`containerKey` в логическом контейнере и каждом связанном сертификате. Общий
экран принимает PKCS#11-список как необязательный: `null`, пустой список либо
ошибки `C_FindObjects*` дают ноль PKCS#11-объектов, но никак не отменяют
CryptoPro-часть. Точный DER-дубликат по-прежнему оставляет PKCS#11-вариант и
помечает соответствующий контейнер представленным. Уникальный CAPI-сертификат
показывается как раньше; любой оставшийся контейнер того же PC/SC-считывателя
теперь появляется отдельной read-only карточкой ключевого контейнера
КриптоПро. Поэтому контейнер без сертификата и без PKCS#11-представления
видим как до входа, так и после него.

После завершения CAPI-вызовов helper читает собственный `/proc/self/maps`,
выбирает уникальные ELF-пути из каталогов пакета КриптоПро и обязательно
добавляет прямо загруженную `libcapi20.so`, даже если `/proc` закрыт
песочницей. Этот список передаётся в UI; диагностика показывает отдельную
строку для каждого фактически загруженного файла и защищена от гонки со старым

## 2026-07-30 — Watson: план исправлений после проверки 1.1.0-1

**Результат проверки владельца:** формирование подписи занимает недопустимо

Кроме того, приложение разрешает подписывать сертификатом, чей срок действия

`PKCS7_DETACHED_SIGNATURE`. Поэтому attached будет передавать `flags=0`, а
detached — только `PKCS7_DETACHED_SIGNATURE`. Пользовательский интерфейс и
текст результата остаются просто интерфейсом подписи без упоминания способа
хеширования.

`notAfter` и сравнивать его с текущим временем смартфона; передавать в модель
явный признак просроченности; стабильно сортировать сертификаты так, чтобы
действующие шли первыми, а просроченные — последними; визуально приглушать
просроченные карточки и скрывать у них действие подписи. Защиту дублировать в
экране сертификата, передавая туда признак просроченности. Выпустить
`1.1.0-2`, добавить статические регрессии, выполнить host-проверки и затем

**Событие:** владелец проверил 0.5.0-4 («стало лучше»), но попросил убрать возврат к базовому экрану смены PIN между шагами и список введённых PIN: тап по операции → сразу экран старого PIN → новый → повтор; как только введён повтор — сразу операция. То есть автосбор 0.5.0-4 (с промежуточным возвратом на `PinChangePage` и итоговым экраном) заменяем прямой цепочкой.

**Прямая цепочка (`PinChangePage`):** контроллер ведёт шаги так, что базовый экран между ними не показывается. `PinPadPage` получил флаг **`autoPop`** (по умолчанию `true` — вход/NFC/метка закрываются сами, как раньше); в цепочке смены PIN `autoPop=false`, поэтому `PinPadPage` сам не закрывается — навигацию ведёт `PinChangePage`: первый шаг — `push` поверх контроллера, каждый следующий — `pageStack.replace` (заменяет предыдущий экран ввода). Над контроллером всегда ровно один экран ввода, поэтому возврат за результатом — простой `pageStack.pop()` (без неоднозначности `pop(page)`, которая в Silica трактуется по-разному). Поток: `onOld` → (unblock: сразу `runOp`; иначе `askNew`) → `onNew` → `askConfirm` → `onConfirm` (совпали → `runOp`; нет → чистим новый/повтор и `askNew` с подсказкой «PIN не совпали»). `runOp` закрывает экран ввода и запускает `changeUserPin`/`changeSoPin`/`unblockUserPin`; результат показывается уже на `PinChangePage` (индикатор → сообщение, «Готово» при успехе, «Ещё раз» при ошибке — перезапуск цепочки). Жест «назад» с экрана ввода делает контроллер активным до запуска операции → `onStatusChanged` отменяет весь поток (`pop`). Списка введённых PIN больше нет — базовый экран виден только в конце.

**Почему только push/replace/pop, без `pop(page)`:** QML на устройстве CI не исполняет, поэтому выбираю проверенные в проекте примитивы. `push` с возвратом страницы используется давно (`openPinPad` и т.п.); `replace` текущей страницы из обработчика — как в `NfcConnectPage` (кнопка «Готово» → `replace`), владелец это проверял; одиночный `pop()` однозначен. `pop(page)` (вернуться к конкретной странице через несколько pop) в разных версиях Silica трактуется по-разному (включая/исключая целевую) — не использую. Прочие вызовы `PinPadPage` (`GenerateKeyPage`, `ImportCertificatePage`, `NfcConnectPage`, `TokenDetailsPage`, `TokenLabelPage`) `autoPop` не передают → поведение самозакрытия сохранено.

**Проблема (отчёт владельца):** v0.0.3-1 на телефоне запускается, ~5 секунд показывает спиннер и вылетает; одинаково без токена, с USB- и с NFC-токеном. v0.0.2 работала.

Прежние static_assert'ы закрепляли именно ошибочную упаковку, поэтому host-компиляция ничего не ловила.

**Фикс:** pack(1) удалён; static_assert'ы переписаны на естественное выравнивание с ветвлением по `sizeof(CK_ULONG)`/`sizeof(void*)` (armv7hl: flags=36, size=76, C_Initialize=4; aarch64: 40/88/8) — 32-битные значения проверяет компилятор armv7hl прямо в CI. Release пакета поднят до `0.0.3-2`.

**Верификация фикса до пуша:** написан харнесс `abi_test.cpp` (dlopen + наш заголовок), скачана **реальная официальная** `librtpkcs11ecp.so` 2.19.0.0 Linux x86_64 с download.rutoken.ru: `C_GetFunctionList` → interface 2.40, осмысленные указатели; `C_Initialize` → CKR_OK; `C_GetInfo` → «Aktiv Co.», «Rutoken ECP PKCS #11 library», версия 2.19, канарейка рядом с буфером не тронута; `C_Finalize` → CKR_OK. Со старым заголовком эта последовательность падала бы на первом же вызове.

**Урок для будущих агентов:** ABI-заголовки нельзя «проверять» static_assert'ами, выведенными из самого заголовка, — сверяться нужно с реальной библиотекой или официальным `pkcs11.h`; pack(1) в PKCS#11 — только Windows.
