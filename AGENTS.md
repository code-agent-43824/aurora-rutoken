# Инструкции для coding-агентов

Этот файл — канонический источник правил проекта для любых coding-агентов. Агент-специфичные файлы (например, `CLAUDE.md`) могут только дополнять его и не должны дублировать или переопределять эти правила.

## Проект

Тестовое приложение для Рутокен ЭЦП 3.0 по USB и NFC на ОС Аврора 5.2 и выше.

- Стек: Qt/C++ + QML, qmake, RPM.
- Application ID: `ru.codeagent43824.rutokentestapp`.
- Доступ к токену: `librtpkcs11ecp.so` (PKCS#11) → `libpcsclite`/`pcscd` → CCID (USB) или NFC-стек.
- Целевые архитектуры: `armv7hl` и `aarch64`; телефон владельца — `armv7hl`.
- Подробные решения и источники: `docs/RESEARCH.md`.
- Дорожная карта и текущий статус: `PLAN.md`.
- Хронология выполненных действий: `docs/JOURNAL.md`.

## Обязательный порядок работы

1. Перед любым действием прочитать `PLAN.md` и верхнюю актуальную запись `docs/JOURNAL.md`.
2. Выполнить `git fetch origin main` и убедиться, что локальная `main` не отстаёт; учитывать изменения других агентов.
3. До изменения кода, CI, конфигурации или структуры записать конкретное действие в `PLAN.md` со статусом `[ ]`/`[~]` и при необходимости пояснить его в `docs/JOURNAL.md`.
4. Только после документирования выполнять действие.
5. Провести проверки, соответствующие риску изменения. Для сборочных изменений дождаться GitHub Actions и проверить фактические логи/артефакты, а не только зелёный статус.
6. После действия обновить `PLAN.md` фактическим статусом `[x]`/`[!]`, добавить верхнюю запись в `docs/JOURNAL.md` и обновить `docs/RESEARCH.md`, если появились новые факты об Авроре или Рутокен.
7. Не оставлять README, план, журнал, research, версию spec и фактическое поведение рассинхронизированными.

## Сборка и выпуск RPM

- RPM собираются в `.github/workflows/build-rpm.yml` с Aurora Platform SDK `5.2.1.200`.
- armv7hl и aarch64 обязаны собираться в независимых чистых matrix jobs. Один job — одна архитектура (`TARGET_ARCH`).
- `ci/build-rpm.sh` обязан подписать пакет официальным публичным тестовым ключом OMP и запустить `ci/verify-rpm.sh`.
- Проверки каждого пакета обязательны: RPM arch, ELF machine, dynamic loader и наличие ожидаемой подписи OMP Regular.
- `ci-latest` публикуется только после успеха и проверки обеих архитектур.
- Пакеты с публичным тестовым ключом предназначены только для режима разработчика.
- **Доставка: релиз `ci-latest` с голыми `.rpm` — ОСНОВНОЙ канал, обязателен.** Matrix jobs не имеют права писать в release: они создают два проверенных per-arch Actions artifacts. Единственный post-build publish job после успеха обеих архитектур скачивает оба artifact, проверяет комплект из четырёх RPM и публикует его с откатом к предыдущему комплекту при ошибке. Артефакты Actions — **второй** канал по просьбе владельца; они по природе **всегда zip** (ограничение GitHub). **Вопрос закрыт: не пытаться «раззиповать» артефакты, не убирать их и не убирать release с голыми RPM.**

## Конвенции UX

- **Терминология устройств.** В пользовательском интерфейсе физический носитель
  называется «устройство» либо «Рутокен». Не использовать «токен» как родовое
  название: NFC-модели могут иметь форму USB-устройства, смарт-карты, брелока или
  кольца. Слово «токен» допустимо во внутренних идентификаторах, исторических
  записях и как точный технический термин PKCS#11. На анимациях/иллюстрациях
  бренд писать по-русски: «Рутокен».
- **Навигация после создания/записи объекта.** После успешного создания или записи объекта в Рутокене (генерация ключевой пары, импорт сертификата и любая будущая операция создания) приложение **возвращается к списку объектов**, а не остаётся на форме ввода параметров. Результат операции (в т.ч. диагностические сообщения вроде итога тестовой подписи) показывается **на списке**. Форма — только для ввода; подтверждение успеха — это новый объект в списке. Правило зафиксировано по требованию владельца (2026-07-23) и применяется ко всем экранам создания. Реализация: форма получает ссылку на экран списка (`objectsPage`), по успеху выставляет на нём флаг показа результата и делает `pageStack.pop()`; для NFC мастер (`NfcConnectPage`) сообщает об успехе сигналом `finishedOk`, и форма возвращается к списку, когда снова становится активной.

## Текущее направление

Стабильная сборка — `1.1.0-2` (v1.1), текущая разрабатываемая —
`1.2.0-2`. Функции USB/NFC, PKCS#11,
PIN, объектов, генерации ключей, сертификатов, удаления и CSR, а также интерфейс
`1.0.0-3` подтверждены на физическом armv7hl-телефоне. `1.0.0-4` содержит
только финальное удаление лишних подтверждений USB-входа; `1.0.0-5` меняет
launcher-имя на «Рутокен», `1.0.0-6` уточняет абстрактный силуэт Slim-C, а
`1.0.0-7` возвращает обязательное совпадение имени иконки с именем пакета
после отказа RPM-валидатора Авроры.
v1.1 закрыта после физической проверки владельцем и независимой проверки CMS.
Текущий этап — v1.2: отдельный опциональный read-only backend внешнего
КриптоПро CSP через динамически загружаемый CapiLite. CSP не поставляется
приложением, а существующий PKCS#11-путь не зависит от него. v1.3–v1.5
последовательно добавляют создание, импорт/удаление и CMS-подпись через CSP;
v1.6 получает тестовый сертификат по PKCS#10 из обоих контуров. Детали и
критерии перечислены в `PLAN.md`.
